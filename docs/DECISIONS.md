# Architecture decision log

Newest last. Each entry: decision, why, and what would make us revisit it. D1 to D5 (the name, the stack, on-premises only, read-only by default, synthetic test data) come from the original scope. Numbers are kept from the project's history, so gaps are decisions about features this edition does not include.

| # | Decision | Why | Revisit if |
|---|---|---|---|
| D6 | Code lives in the public GitHub repo `OpenSourceCybersecurity/OS-DataScope` under Apache-2.0. Work lands through feature branches and pull requests reviewed by a maintainer; `main` is never pushed to directly. | One place for code, issues and reviews, open to the community. | The project moves to a foundation or another host. |
| D7 | .NET 10 LTS, ASP.NET Core minimal APIs, EF Core 10 + Npgsql, PostgreSQL 16. Central package versions (`Directory.Packages.props`) with lock files and warnings-as-errors. | Spec stack (D2). Lock files make builds reproducible offline. | .NET 10 support ends (Nov 2028). |
| D8 | Four projects: `Core` (rules, no I/O), `Persistence` (EF, queue, audit), `Api`, `Worker`. Scanners plug into the worker behind `IScanExecutor`. | Keeps the risky parts (parsers, AD, ACLs) testable without a database or Windows. | A module needs its own process or release cycle. |
| D9 | Job queue is a PostgreSQL table claimed with `FOR UPDATE SKIP LOCKED`, with leases, checkpoints and a retry cap of 5. No message broker. | One less service for an SMB to install and patch. Handles the expected volume (a few servers, one scan at a time each). | Many workers or thousands of jobs per hour. |
| D10 | Admin audit log is append-only and hash-chained (SHA-256 over length-prefixed fields). A database trigger rejects UPDATE, DELETE and TRUNCATE; `/api/v1/audit-log/verify` re-checks the chain. Details are stored as `json`, not `jsonb`, so the exact hashed text is kept. | Tamper evidence that an auditor can check themselves. A DB superuser can still drop the trigger, so this is evidence, not prevention. | We add signed off-box export (M5). |
| D11 | Production sign-in is Windows Negotiate (Kerberos, NTLM fallback). Roles come from AD group SIDs in config, not group names. Every endpoint is deny-by-default. A fake Development user exists only when the environment is Development, and the API refuses to start otherwise. | No separate passwords to manage; SIDs survive group renames. | A customer needs SSO beyond AD. |
| D12 | Five roles: PlatformAdmin, SecurityAnalyst, Auditor, DataOwner, Viewer. DataOwner sees nothing platform-wide until scoped owner views exist (M4). | Least privilege from day one. | Owner portal design (M4). |
| D13 | Managed servers are identified by DNS or NetBIOS host name only. IP addresses, ports, UNC paths and anything else are rejected. | Kerberos needs names; strict parsing closes injection paths into later SMB and WMI calls. | A customer has no working DNS. |
| D14 | The UI is served by the API from the built `web/dist` with a strict CSP (`default-src 'self'`). Fonts are self-hosted (`@fontsource`), so the product never reaches the internet. | On-prem networks are often air-gapped. | Never for runtime assets. |
| D15 | The M0 worker runs a dry-run executor only. It never touches a share. | Spec: no live scanning in M0. | M1 adds share enumeration. |
| D16 | Windows CI builds and runs non-database tests. Database tests run on Linux against PostgreSQL 16. | GitHub's Windows runners do not offer service containers. | We add a Windows PostgreSQL step or a self-hosted Windows lab runner (needed by M3 anyway). |
| D17 | The scanner lists shares with `NetShareEnum` level 1 and walks them folder by folder with the OS directory APIs. It reads names, sizes, timestamps and attributes only. It never opens a file in M1. | Level 1 needs no admin rights on the file server. Not opening files means the scan cannot change content or last-access times of files. | M2 adds reading file contents for classification, with its own safeguards. |
| D18 | Scans run as the worker's Windows service identity. We recommend a group Managed Service Account (gMSA) with Read on the shares. Data Scope stores no scan password. | Least privilege. No secret to leak or rotate. | A customer can't use gMSAs; then we add DPAPI-protected credentials. |
| D19 | Junctions, directory symlinks and mount points are never followed; each is recorded as a gap. Files that are reparse points (deduplicated files, cloud placeholders) are recorded as normal files, since they are never opened. | Prevents loops and walking off the share. Data Deduplication is common on file servers and would otherwise hide most files. | |
| D20 | Administrative and system shares (`C$`, `ADMIN$`, `IPC$`, printers) are recorded but can never be included in a scan. New disk shares are included by default. Admins can exclude any disk share; this is audited. | Admin shares duplicate real data, and reading them needs admin rights. | |
| D21 | The list of folders still to visit (the frontier) is stored per job in the database. Each folder's results commit in one transaction with its removal from the frontier. | Pause, crash, restart or lease takeover resumes exactly where it stopped, with no double counting. | |
| D22 | Something is marked removed only after a complete listing of its parent folder that did not include it. A folder the scan could not read never causes its contents to be marked deleted. | A permissions change must not look like data being deleted (no false certainty). | |
| D23 | Folder uniqueness uses a SHA-256 of the upper-cased share-relative path, because Windows paths can exceed PostgreSQL's index entry limit. Names are compared case-insensitively like NTFS. Unpaired UTF-16 characters are stored with replacement characters and flagged as a gap. | Correctness on real-world paths. | |
| D24 | Hard limits per scan: depth 64, 200,000 entries per folder, 20 million entries per job. All are configurable. Hitting one is a visible gap, never a silent stop. | Bounded resource use (project rule). | Benchmarks in M5. |
| D25 | When the UI is served by a Data Scope server, **Servers & scans** and **Shares** use live data. Every other screen stays on the synthetic demo, with a banner saying so, until its milestone lands. The standalone build stays fully synthetic. | Keeps the prototype useful while making progress visible. | Each later milestone moves its screens to live data. |
| D26 | The lab install (pulled forward from M5 at the owner's request) is a zip of self-contained win-x64 builds plus `Install-DataScope.ps1`, not an MSI. It needs PostgreSQL 16 installed first ("bring your own PostgreSQL"). The installer upgrades in place when run again. | Gets a real lab running now with nothing else to install, and the script is readable and testable in CI. | M5 decides on an MSI and whether to bundle PostgreSQL. |
| D27 | The API runs as the virtual account `NT SERVICE\DataScopeApi`; the scanner runs as the scan account. The two never share an identity. | A virtual account needs no password and acts as the computer on the network, so Kerberos works without registering an SPN. The scan account's share access stays out of the web process. | A customer needs the API on a different host name than the computer's (then an SPN is needed). |
| D28 | Server settings live in `%ProgramData%\DataScope\config\datascope.json`, written by `DataScope.Setup` and loaded last by both services. The installer restricts the folder to Administrators, SYSTEM and the two service identities before any secret is written. | The database password needs to be on disk somewhere; a locked-down file is the standard on-prem pattern and easy to back up. | M5 adds DPAPI encryption of the connection string. |
| D29 | `DataScope.Setup` creates a dedicated login role (never a superuser, no CREATEDB or CREATEROLE) that owns the Data Scope database, with a 40-character generated password. The PostgreSQL admin password is used once and never saved. Re-running keeps the existing password unless `--rotate-password` is given. | Least privilege, with no password for anyone to choose or reuse. | M5 splits a migration owner from a runtime role with DML only. |
| D30 | HTTPS uses a certificate from `LocalMachine\My`, chosen by thumbprint. Without one the installer creates a 2-year self-signed RSA-3072 certificate and says so. The listener is HTTP/1.1 only. | Customers' internal CAs issue into that store. Windows sign-in (Negotiate) does not work over HTTP/2. | Answers open question 2 from M0. |
| D31 | Every state-changing API request must carry an `X-DataScope-Client` header; the UI always sends it. Missing it gets 403 (after authentication, so anonymous callers still get 401). | Browsers attach Windows sign-in automatically, which makes cross-site request forgery possible. Forms can't set custom headers, and cross-origin scripts would need a CORS preflight the API never grants. | We add cookie sessions (then use antiforgery tokens). |
| D32 | When `/api/v1/me` returns 401, the UI shows a sign-in help page and never falls back to demo data. A signed-in user with no role sees a "no access yet" page. | Showing the synthetic company on a real server could be mistaken for real findings. | Never. |
| D33 | CI builds the install package and runs it on a fresh GitHub Windows Server runner under Windows PowerShell 5.1, with the runner's preinstalled PostgreSQL, a local scan account and a local admin group. It signs in with NTLM, scans a share, checks nothing changed, upgrades and uninstalls. | Proves the installer, services, HTTPS, sign-in and SMB scanning on real Windows on every change. | A domain-joined self-hosted runner becomes available (then Kerberos, gMSA and remote shares move into CI too). |
| D34 | Classification runs inside the scan job, after the walk, as a second phase ("classify"). It reads only files the walk saw in this job that are new, changed (size or modified time), last read under an older policy, or failed last time for a reason that may pass (access denied, offline, I/O error, timeout). Progress is checkpointed by file id. | Rescans stay cheap: unchanged files are never opened again. One job per server keeps the existing pause, resume and lease logic. | Large servers need classification on its own schedule or in parallel workers. |
| D35 | The detectors are a C# port of the prototype's rules with the same test vectors, plus a synthetic precision and recall corpus. Every regex uses .NET's non-backtracking engine, so time is linear in the text whatever a file contains. Policy version is now `2026.10-r4` (r3 plus "D.O.B." dates and more password placeholders such as `${VAR}` and `%VAR%`). | Same behaviour as the prototype users have seen, and no regex denial of service. | A customer needs custom patterns (they must use the same engine). |
| D36 | Evidence is at most 3 snippets per rule per file, each the masked value with 30 characters either side. The surrounding text comes from a copy of the file text where every digit is `#` and every secret value is `•`, so a second number or a password next to a match is never stored. SSNs and cards keep their last 4 digits, as receipts do. Names next to a match can appear in evidence. | Reviewers need enough context to judge a false positive; nothing stored is a usable identifier. | Customers want no context at all (a setting), or evidence encryption lands (D44). |
| D37 | Content readers: plain text (BOM, strict UTF-8, then Latin-1; UTF-16 without BOM detected), DOCX, XLSX, PPTX (and macro-enabled variants, read as text only), and the text layer of PDF via PdfPig (Apache-2.0). Legacy `.doc/.xls/.ppt`, archives, images and OCR are not read and say so. Limits: 1,000,000 characters, 50 MB Office, 25 MB PDF, 200 PDF pages, 10,000 archive entries, 256 MB decompressed, 30 s per file. All configurable under `Scanner:Content`. | Covers where SMB file shares keep most personal data, with bounded cost. | Customers need `.doc`/`.xls`, `.msg` or OCR. |
| D38 | Office files: the entry count is read from the zip's end record before the archive is opened; every entry is read through a stream that stops at its declared size and at the 256 MB total, whatever the headers claim; XML refuses DTDs and never resolves external entities; text is copied in 4 KB chunks so one huge text run cannot fill memory. PDF: every compressed stream's decoded size is measured before PdfPig decodes it, against the same 256 MB budget; LZW streams that could exceed it are refused. A file that trips any limit is "Unreadable", not partly trusted. | Zip bombs, XML entity attacks and PDF compression bombs are tested in CI with generated files. | |
| D39 | Files are opened read-only with full sharing (users editing a file are never blocked). On Windows they are opened with `FILE_FLAG_OPEN_NO_RECALL`, and files marked Offline, RecallOnOpen or RecallOnDataAccess are skipped before opening, so a scan never downloads OneDrive or Azure Files placeholders or recalls from tape. Windows may still update a file's last-access time; Data Scope never asks for write access, which preventing that would need. | Read-only is non-negotiable; recalls could cost money and fill disks. | Customers rely on last-access times for archiving (then document the volume setting). |
| D40 | Parsers run inside the scanner service process, not a separate sandboxed process. | The scanner already holds read access to every share, so a parser compromise gains little beyond that; limits above bound resource abuse; process isolation adds real install complexity. | A parser vulnerability is found, or we add formats with a worse security history. Recorded as an open risk in the threat model. |
| D41 | A file's label is computed from its findings by the versioned policy. A file whose contents were not read is "Unknown", never Internal or Public. A failed re-read for a temporary reason keeps the previous result and its date, and records the new state. | No false certainty: "not read" is a coverage gap. | |
| D42 | People can override a file's label with a reason. Overrides are append-only rows plus an audit-log entry; the latest row is in force; removing an override is another row. The policy label stays visible next to it, and the UI flags files read again after the last review. PlatformAdmin and SecurityAnalyst may override. | False positives need a durable, explainable decision; auditors see who decided what and why. | M4 lets data owners review their own files. |
| D43 | Evidence snippets are shown to PlatformAdmin, SecurityAnalyst and Auditor. Viewers see categories, confidence and counts only. | Least privilege over the most sensitive thing Data Scope stores. | |
| D44 | Evidence is stored in the database unencrypted for now (it is already masked; see D36). Field encryption with a DPAPI-protected key moves to M5 with the other secrets work. | One key-management design for settings, credentials and evidence instead of three. | A pilot customer needs it sooner. |
| D45 | Security descriptors are parsed by Data Scope's own bounds-checked parser (MS-DTYP self-relative format), not `System.Security.AccessControl`. Bytes are capped at 192 KB, every offset and count is checked, and a damaged descriptor is recorded as "Unreadable". The parser is fuzzed with 5,000 random corruptions in CI. | The .NET classes only work on Windows, and the API and tests run on Linux too. Parsing untrusted bytes from a file server must never crash or hang the service. | |
| D46 | Effective access is evaluated the way Windows does over SMB: entries in stored order, each right decided by the first entry that mentions it, generic rights mapped, and the result is what both the share permission and the NTFS permission allow. The owner always has read and change-permissions rights unless an OWNER RIGHTS entry exists. Change permissions or take ownership counts as Full control. | Matches what a user can really do, including unusual (non-canonical) entry orders. | |
| D47 | Every answer is a range: what Data Scope can show (lower bound) and what is possible (upper bound), with a certainty. "Likely" when both are equal, "Partial" when any input was missing, "Unknown" when the folder's permissions could not be read. Unreadable share permissions make the lower bound "no access". Entries Data Scope cannot evaluate (conditional entries, unresolved memberships) widen the range instead of guessing. The UI says "possibly" for anything not certain. | Project rule: never claim full effective permissions when resolution is incomplete. | |
| D48 | It is never called "confirmed". Results say they are computed, not a Windows access check, and not evidence that anyone opened a file. A real `AuthzAccessCheck` on the file server is deferred. | Honest labelling; a live check needs code on the file server. | A customer wants on-demand verification (M5+). |
| D49 | Share permissions (`NetShareGetInfo` level 502) and the file server's local groups (`NetLocalGroupGetMembers`) need administrator rights on the file server. Without them Data Scope records "AccessDenied" and shows ranges. Data Scope does not ask for admin rights by default. | Least privilege; the docs explain what admin rights add. | |
| D50 | Local groups of the file server (BUILTIN\Users, BUILTIN\Administrators and the server's own groups) are read per server during each scan. Groups whose members could not be read count as "possibly" containing anyone. | NTFS entries on file servers very often use BUILTIN\Users. | |
| D51 | Directory sync reads users, groups, computers, foreign security principals and memberships from one domain over LDAP, read-only, with paged searches and ranged `member` retrieval. Each sync is an immutable snapshot; the last 10 are kept. A failed sync never replaces the last good one. Syncs run daily and on request (admins, audited). | Reproducible explanations now, and review campaigns (M4) can pin a snapshot. | Multi-domain forests (V2). |
| D52 | LDAP sign-in uses the service account with Negotiate, signing and sealing on Windows. A user name and password are only sent over LDAPS, except in Development where `AllowUnencryptedPassword` exists for the Samba test DC. | No cleartext credentials on the network. | |
| D53 | Group nesting is resolved per user: nested security groups, primary group, SID history, and the implicit network-logon groups (Everyone, Authenticated Users, NETWORK, This Organization). Distribution groups never grant access. Loops are found and reported, and don't break resolution. Groups with members that could not be resolved, such as members from another forest, make membership "possibly". | Same token Windows builds for an SMB session, without guessing about the parts it can't see. | |
| D54 | "Open to everyone" means what an ordinary enabled domain user with no extra groups gets: Everyone, Authenticated Users, Domain Users and local groups containing those. Exposure lists folders holding Confidential or Restricted files that this user can or might read. | One clear definition customers can act on. | |
| D55 | Permissions are read per folder, not per file. Answers about files are "for files that inherit the folder's permissions" and say a file with its own permissions can differ. CREATOR OWNER entries are noted, not evaluated. | Reading every file's descriptor multiplies scan cost; nearly all files inherit. | File-level descriptors for sensitive files only (M4 or M5). |
| D56 | Each distinct descriptor is stored once (by SHA-256) with its entries parsed alongside; folders and shares point at it. A folder whose descriptor changed between scans gets a drift row. A failed read clears the old descriptor so stale permissions are never shown as current. | Most folders inherit identical permissions, so storage stays small; drift reporting has data from day one. | Drift screen and alerts (M4). |
| D57 | The "Who has access" screen and the API compute access on request from the stored snapshot and descriptors, with caches keyed by snapshot and descriptor ids. Lists of places show permission boundaries (share roots and folders with their own entries or inheritance turned off), not every inheriting folder. | Correct for any folder without precomputing a huge access matrix. | Customers with millions of boundaries (then precompute per snapshot). |
| D58 | Deferred from M3: file-level ACLs, Dynamic Access Control central policies, a live Windows access check, a drift screen, a precomputed access matrix, and multiple domains. | Keeps M3 reviewable. | |
| D59 | An owner is assigned to a folder (a share through its root folder) by a PlatformAdmin, from enabled users in the latest directory sync, with an optional backup owner and a review frequency (quarterly, twice a year, yearly). Assignments are never edited: a change ends the current row and adds a new one, so ownership history is kept. Data Scope only suggests owners (the folder's Windows owner, people with Modify or Full directly). | Owners are a business decision; history answers "who owned this in March". | Owners need to be groups or roles, not people. |
| D60 | A campaign freezes, for every owned folder in scope, the folder's NTFS entries and the people each one reaches in the latest directory sync, into append-only tables. Each review carries a SHA-256 seal of its frozen content; `GET /campaigns/{id}/verify` and both evidence exports recompute it. Folders whose permissions were not read are skipped with the reason, never reviewed on guesses. | Auditors need what the owner saw, not today's state. A seal makes later edits detectable. | |
| D61 | Owners need no Data Scope role. `/my/*` endpoints are open to any signed-in person and scoped on the server by SID: the owner, the person they handed the review to, and the backup owner once the review is escalated. Anything else is 404, so the portal does not reveal which reviews exist. | Managers are many and change often; giving each a role would be busywork and wider access than they need. | |
| D62 | Decisions are Keep, Remove, Investigate and Exception. Remove, Investigate and Exception need a reason of at least 10 characters; an exception needs an end date within a year. Decisions are append-only revisions; the newest per entry counts. Only allow entries for non-administrative trustees need a decision; deny entries, administrators, SYSTEM and CREATOR OWNER are shown but not decided. Submitting needs every required entry decided and an explicit confirmation, and makes the decisions final. | Clear choices a manager can make; reasons are the audit evidence. | |
| D63 | (Tasks removed in D173; decisions are kept as evidence.) Submitting turns Remove into a "remove access" task and Investigate into an "investigate" task for IT. Data Scope never changes permissions or groups. A removal goes Open, Approved, Implemented (by a person, with a note), Verified (only by a scan that read the folder after the change and found no entry for the trustee), Closed. The person who asked for a change cannot approve or implement it. | Read-only product (D4). Verification by rescan proves the change instead of trusting a checkbox. | Customers want Data Scope to make the change (V2, with approvals). |
| D64 | Review email goes through the customer's own SMTP relay (STARTTLS required outside Development) from a database outbox: idempotent keys, claimed with `FOR UPDATE SKIP LOCKED`, retried at 1, 5, 30 and 120 minutes, then marked failed. Without SMTP settings messages are marked skipped and reviews still wait in Data Scope. | No third-party mail service. The outbox survives restarts and never sends twice. | Customers need Microsoft Graph mail (cloud). |
| D65 | Emails carry no token and no decision links: only a link to the owner portal, where the reader signs in with Windows. The body says the email cannot approve anything. | A forwarded or phished email grants nothing. | |
| D66 | Reminders: the assignment notice, a week before, the day before and the due day (never on the first day), then weekly while overdue. Three days after the due date the backup owner gets an escalation and can complete the review; the escalation is logged. | Enough nudges to finish without nagging. | Customers ask for configurable schedules. |
| D67 | An owner or escalated backup can hand a review to an enabled colleague; an administrator can reassign any open review. The owner can still decide. People are chosen through `/my/people`, which only owners may call and which returns names of enabled users only. | Managers delegate in practice; the trail records who decided and in what capacity. | |
| D68 | Closing a campaign is a PlatformAdmin action. Unsubmitted reviews keep their decisions, are marked "closed before submission", and create no tasks. | A deadline must be enforceable without inventing decisions. | |
| D69 | Evidence exports: CSV (one row per frozen entry with the decision in force, the task and whether the seal still verifies, formula-safe cells) and JSON (everything, including every decision revision, review history and task history). Both are audited. | CSV for spreadsheets, JSON for complete evidence. | Auditors want signed PDF reports (M5). |
| D70 | Deferred from M4: Data Scope making changes, recurring campaigns created on a schedule, file-level reviews, review of share permissions (only NTFS is reviewed; the share permission is shown as context in access), certification of group membership, and owner portal reports. | Keeps M4 reviewable. | |
| D71 | M5 is split into reviewable parts: M5a reports and the live overview (this PR); M5b hardening (encrypted settings with DPAPI, split database roles, rate limiting, TLS and CSP tightening, retention and backup); M5c customer packaging (MSI, signing, SBOM, load tests). | One milestone per PR; reports are what a pilot needs first. | |
| D72 | Reports are built on the server and come as CSV or as a print-ready HTML page; PDF comes from the browser's own "Save as PDF" or Microsoft Print to PDF. No PDF library ships. | No new dependency or licence to vet, full Unicode file names, and nothing leaves the server. | Customers who need signed PDF reports. |
| D73 | Every report opens with the same statement (A15): generated when and by whom, scope, latest scan, share coverage, gaps and unread files, classification policy, directory sync, and how much access could not be resolved, followed by plain-language limitations. CSV puts it above a blank line and the table. | One rule for every report, and the statement travels with the file. | |
| D74 | Reports stop at 100,000 rows (CSV) or 5,000 (page) and say so in the statement; the group matrix and risky permissions look at no more than 50,000 places where permissions are set. Reports are built in memory per request. | Bounded memory and time. | Background report jobs for very large estates. |
| D75 | Risky permissions use fixed, explained rules, not a score. High: Restricted files any domain user can read. Medium: Confidential files any domain user can read, Restricted files they might read, or any domain user can change files. Low: sensitive files whose permissions could not be read, deleted or disabled accounts named in permissions, people given access directly, and entries out of canonical order. Each row says why and suggests a fix for IT. | Explainable severity (PRD module F). | Customer-tunable rules. |
| D76 | Report access follows the existing roles: posture reports need ReadPosture; review evidence needs ReadReviews. The report list shows only what the caller may run. Each export is audited with report, format, scope and row count. Report pages have no scripts and every value is HTML-encoded. | Same boundaries as the screens. | |
| D77 | The overview shows files by years since last write, not a growth trend, because scans keep only current totals. Last-access time is never used. | Honest with today's data. | Volume trends need per-scan history (M5b, with retention). |
| D78 | Passwords in the settings files (the two database connections, the SMTP and directory passwords, the backup key) are encrypted with Windows DPAPI, machine scope, with Data Scope's own entropy, and stored as `dpapi:<base64>`. Values are decrypted as settings load; an unreadable value stops start-up with a message naming the setting and the fix. Plain values from older versions still load, `DataScope.Setup protect` (run by the installer) encrypts them, and `check` warns while any remain. Off Windows (development, CI) values stay plain. | A copied settings file or config-folder backup no longer reveals passwords, with no key to manage. Machine scope lets both services and setup read them. | A customer needs the settings readable on another server (then: re-enter them there, see "Move to a new server"). |
| D79 | Two database logins. `datascope_owner` owns the database and schema and is used only by setup (migrations, backup, restore); its connection lives in `config\setup-only\database-owner.json`, a folder only Administrators and SYSTEM can open. The services use `datascope_app`, which can read and change rows but cannot change the schema, truncate, write the migrations table, or update or delete rows in the audit log or review events. Grants are refreshed after every migration. An installation from before this split is converted by running `setup database` once (the installer asks for the PostgreSQL admin login to do it). | A compromised service can no longer rewrite history or the schema; the append-only tables are enforced by PostgreSQL, not only by triggers. | |
| D80 | Rate limits per signed-in user (by SID): 600 API requests a minute; 300 a minute per address before sign-in; 20 report exports per 5 minutes. Over the limit the API answers 429 with Retry-After. All are settings (`RateLimits`). | Stops a runaway script or a stolen session from exhausting the server; generous for people. | Large customers with automation need higher limits (raise the setting). |
| D81 | HTTPS accepts TLS 1.2 and 1.3 only; no Server header; HSTS outside Development. The content policy allows nothing inline (no `unsafe-inline` styles), no plugins (`object-src 'none'`), and resources only from the same origin (`Cross-Origin-Resource-Policy: same-origin`); API responses are `no-store`. Report pages get their own policy allowing only their one inline stylesheet by its SHA-256 hash. | Closes the remaining XSS and caching gaps; old TLS versions are refused by default on current Windows anyway. | |
| D82 | Every finished scan adds one row per share to `share_scan_history` (files, size, Restricted, Confidential, files not read, gaps). The overview's **Over time** charts use the last 365 days: one point per day built from each share's latest scan that day, thinned to at most 60 roughly weekly points. | Trends need history; one small row per share per scan is cheap. This replaces D77's limitation. | |
| D83 | Retention runs daily in the scanner service and deletes, in batches: files and folders removed from their share over 365 days ago, permission changes over 730 days, gaps of superseded scans over 365 days, sent/skipped/failed emails over 180 days, and scan history over 1,095 days (each share's latest row is kept). Each period is a setting; 0 means keep forever and anything else must be at least 30 days. Review evidence, reviewer labels (and the files they label) and the audit log are never purged. Every purge that removes something writes an audit entry with the counts. | Bounded growth without losing evidence auditors rely on. | A customer's records policy needs different periods (change the settings). |
| D84 | Backups are made by setup with PostgreSQL's own `pg_dump` (custom format) and sealed in a Data Scope file (`.dsbackup`): a readable header (version, schema, key id, time; no customer data) followed by AES-256-GCM chunks of 1 MiB, each authenticated together with the header, its position and whether it is the last. A changed, reordered or cut-off file is refused. pg_dump and pg_restore get the password through the environment, never the command line. | Backups often end up on file shares and USB disks; they hold the whole inventory. Standard tools for the dump itself, so a DBA can still reason about it. | |
| D85 | One random 256-bit backup key per server, created by the first backup and kept DPAPI-encrypted in the admin-only owner settings. Each backup names its key's id. `DataScope.Setup backup-key` shows the key (64 hex digits in groups of 8) for the admin to keep in a password manager; restoring on another server needs it (`DATASCOPE_BACKUP_KEY` or a prompt).
